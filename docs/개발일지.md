## 결정과 이유

- **조치 결과는 등록(Main Data) 행에 둡니다.** 한 건에 조치 결과는 하나(종료 때 한 번)라 문의·회신처럼 차수 행이 필요 없고, 관리자 조회·통계에서 건 단위로 바로 쓰기 위함입니다.
- **종료한 건은 다시 열지 않습니다.** 후속 요청으로 상태를 Submitted 로 되돌리면 조치 결과와 상태가 어긋나기 때문입니다. 1달 팝업에서 종료 건을 빼고, 종료 건의 후속 요청 주소로 들어오면 새 지원 요청 안내를 보여 줍니다. 관리자 상세에서도 종료 건은 AI 회신 입력을 숨깁니다(회신 저장이 상태를 Answered 로 되돌리므로).
- **완료일은 등록일 이후·오늘 이전**만 받습니다. 달력 입력에도 같은 범위(min/max)를 걸었습니다.
- **영상 길이를 못 읽으면 막지 않고 경고합니다.** 브라우저가 코덱을 모르는 형식(예: 일부 휴대폰 HEVC 영상)은 길이를 알 수 없는데, 이때 막으면 정상 파일도 못 올리기 때문입니다. 8초 안에 못 읽어도 같은 처리입니다.
- **첨부 종류는 MIME 우선, 없으면 확장자로** 판정하고, 사진·영상이 아니면 막습니다.
- 옛 브라우저 저장 데이터·옛 엑셀(조치 열 없음)은 그대로 읽히며 두 필드는 빈 값입니다. 옛 데이터의 종료 건은 조치 결과가 「-」로 보입니다.

## 결정과 이유

- **매뉴얼 PDF 는 리포에 넣지 않습니다.** 회사 저작물이고 공개 리포이며 용량도 큽니다. 로컬 `docs/source/manual/` 에만 복사하고 `.gitignore` 에 `docs/source/manual/`·`*.manual.json`·`manual-index/` 를 넣었습니다. `git check-ignore` 로 확인했습니다.
- **pdf.js 를 classic script 로 넣었습니다.** 3.11 판은 UMD(`window.pdfjsLib`)라 module 없이 읽힙니다. 파일로 열기(file://)에서는 브라우저가 Worker 를 막는데, worker 스크립트를 일반 스크립트로 먼저 읽어 두면 pdf.js 가 그것을 같은 화면에서 씁니다(`globalThis.pdfjsWorker`). 웹 주소에서는 Worker 로 돕니다. 두 경우 모두 실제 브라우저에서 추출을 확인했으므로, 요청에 적힌 대안(파이썬 JSON)은 **대체가 아니라 보조 경로**로 두었습니다(PDF 가 너무 크거나 느린 PC 용). pdf.js 는 「매뉴얼 근거」 화면에서 PDF 를 고를 때만 읽어 들여 첫 화면이 무거워지지 않습니다.
- **뽑은 글자는 IndexedDB 에 둡니다.** 4종 합쳐 약 1.6MB 라 기술지원 DB 와 함께 쓰는 localStorage(약 5MB)에 넣기엔 큽니다. IndexedDB 를 못 쓰면 메모리에만 두고 화면에 알립니다.
- **목차 정규식을 잘게 나눴습니다.** 처음에 점선 리더를 한 식(중첩 반복)으로 잡았더니 pdftotext 결과의 긴 점선 줄에서 역추적이 폭발해 멈췄습니다. 「줄 끝 쪽 표기 → 앞부분에 리더가 있는지」로 나눠 선형으로 만들고, 400칸 점선 줄 30개가 0.5초 안에 끝나는지 테스트로 묶었습니다.

- **들여쓰기를 남기도록 글자 뽑기를 바꾼 이유**: DE-7·LE-7 운전자 매뉴얼 목차는 장과 절 모두 쪽 번호가 붙어 있어 들여쓰기 말고는 둘을 가를 단서가 없습니다. 파이썬 스크립트도 빈칸을 줄이지 않게 바꿨습니다(발췌·검색 조각은 여전히 빈칸을 줄여 씀).
- **두 단 목차의 단 사이**: pdf.js 는 단 사이를 빈칸 조각 하나(폭이 빈칸 전체)로 주기도 해서, 빈칸 조각은 끝 위치를 늘리지 않게 하고 글자 높이의 1.8배 넘는 빈칸을 넓은 빈칸으로 남깁니다. 100D-9V 의 실제 단 사이가 27.4pt(글자 11pt)라 처음 기준(2.5배=27.5pt)에 0.1pt 차로 걸리지 않았던 것을 실측으로 찾았습니다.
